- 关联文档：
  - `PRD.md`

- 文档版本：v0.1

## 2. 文档目标

本项目的核心体验并不在于“3D 画面是否复杂”，而在于：

- 用户什么时候算失败
- 用户什么时候算成功
- 系统是否能稳定、可解释地给出反馈

本文件聚焦回答以下问题：

- 训练状态有哪些
- 失败规则如何定义
- 成功规则如何定义
- 多个成功目标如何共存
- 规则触发顺序如何处理
- 如何避免误判和重复触发

## 3. 规则设计原则

### 3.1 结果必须可解释

用户应当能直观看懂为什么成功或失败。

这意味着：

- 不采用过于隐晦的判定标准
- 不采用用户难以理解的物理数值阈值
- 优先使用几何关系清晰的判定

### 3.2 判定要稳定，宁可简单

MVP 阶段宁可规则简单明确，也不要引入过度复杂的“接近真实”的条件。

例如：

- 车位成功只看四轮是否全部在框内
- 判定线成功只看车头点是否过线

### 3.3 训练状态只能有一个最终结果

一次训练的结果只能是以下三种之一：

- 进行中
- 成功
- 失败

不能出现：

- 同时成功又失败
- 成功后继续被判失败
- 失败后继续触发成功

### 3.4 最终状态一旦成立，应锁定

当训练进入成功或失败状态后，MVP 建议立即冻结本轮结果，直到用户主动重置。

## 4. 训练状态机设计

## 4.1 状态定义

MVP 建议采用以下状态：

- `idle`
- `running`
- `success`
- `failure`

含义说明：

- `idle`: 地图已加载但尚未开始本轮训练
- `running`: 用户正在驾驶，规则持续检测中
- `success`: 本轮训练已成功
- `failure`: 本轮训练已失败

## 4.2 状态流

```text
地图加载完成
   ↓
idle
   ↓
用户开始驾驶 / 进入驾驶模式
   ↓
running
   ↓
┌──────────────────────┬──────────────────────┐
│ 满足失败条件            │ 满足成功条件            │
└──────────┬───────────┴──────────┬───────────┘
           ▼                      ▼
        failure                success
           │                      │
           └────────→ reset ←─────┘
                          │
                          ▼
                        idle
```

## 4.3 状态行为建议

### `idle`

- 车辆位于出生点
- 不触发训练结果
- 用户可点击开始或直接输入驾驶操作进入 `running`

### `running`

- 持续处理输入
- 持续推进车辆状态
- 持续执行碰撞与成功判定

### `success`

- 停止本轮规则检测
- 可停止车辆输入，或允许极短缓冲后锁定
- 显示成功提示

### `failure`

- 停止本轮规则检测
- 停止车辆输入
- 显示失败提示

## 5. 每帧规则处理顺序

MVP 建议每个更新周期按固定顺序执行：

1. 读取输入
2. 更新车辆运动状态
3. 更新车辆参考点
4. 执行失败判定
5. 若未失败，则执行成功判定
6. 若触发最终状态，则锁定结果
7. 更新 HUD 和提示

## 5.1 推荐顺序原因

核心建议是：

- 失败优先于成功

即：

- 如果同一帧既发生碰撞又满足成功条件，优先判定失败

原因：

- 训练逻辑上更保守、更符合直觉
- 可避免“撞着进车位也算成功”的歧义

## 6. 失败规则设计

## 6.1 MVP 失败条件

MVP 仅包含两个失败条件：

- 车辆碰撞到障碍物
- 车辆驶出地图边界，且地图开启出界失败

## 6.2 失败条件一：碰撞障碍物

### 定义

当车辆碰撞体与任一障碍物碰撞体相交时，判定失败。

### 参与碰撞的对象

- 静态轿车
- 静态 SUV
- 矩形
- 正方形
- 房子
- 围墙

### 不参与失败碰撞的对象

- 车位框
- 判定线
- 出生点

### 判定草图

```text
┌──────── obstacle ────────┐
│                          │
│      ┌──────────┐        │
│      │ vehicle  │        │
│      └──────────┘        │
│                          │
└──────────────────────────┘

车辆碰撞盒与障碍物碰撞盒重叠 => failure
```

## 6.3 失败条件二：驶出边界

### 定义

若地图 `scene.boundary.enabled = true` 且 `failOnExit = true`，则车辆离开地图边界范围时失败。

### 地图边界建议

若地图中心为原点，地图尺寸为：

- `width`
- `height`

则平面边界可定义为：

- `x ∈ [-width/2, width/2]`
- `z ∈ [-height/2, height/2]`

### 判定对象建议

MVP 建议以车辆主车体中心点或主碰撞盒范围判定是否出界。

更保守方案：

- 只要车体主碰撞盒任意部分超出边界即失败

更宽松方案：

- 仅当车体中心点超出边界才失败

MVP 推荐：

- 采用主碰撞盒超界失败

原因：

- 与“碰到障碍物即失败”的体验更统一

## 6.4 失败状态反馈

MVP 建议失败时给出以下反馈：

- 状态提示：失败
- 原因提示：碰撞障碍物 / 驶出边界
- 提供重置按钮

## 7. 成功规则设计总览

MVP 支持两类成功目标：

- `parking_zone`
- `trigger_line`

同一张地图允许同时存在两类目标。

默认规则：

- 只要任一成功目标达成，即判定成功

## 7.1 成功判定总流程

```text
running
  ↓
先检查是否 failure
  ↓
若否
  ↓
依次检查 goals[]
  ↓
只要某个 goal 成功
  ↓
success
```

## 7.2 多目标并存逻辑

当地图同时存在多个目标时：

- 多个车位框并存：任一车位框达成即可成功
- 多条判定线并存：任一判定线达成即可成功
- 车位框和判定线并存：满足任一目标即可成功

## 8. 车位成功规则设计

## 8.1 规则定义

若车辆四个车轮参考点均落在某个 `parking_zone` 范围内，则判定成功。

这是当前已确定的业务规则，不再使用“车身主体进入”或“中心点进入”的宽松判定。

## 8.2 判定对象

### 目标对象

- `goal.type = parking_zone`

### 车辆参考点

- 左前轮
- 右前轮
- 左后轮
- 右后轮

## 8.3 几何思路

停车框本质上是一个可旋转矩形区域。

判定方法建议：

1. 获取四个轮点在世界坐标中的位置
2. 将轮点转换到车位框局部坐标系
3. 检查四个轮点是否都落在矩形边界内

## 8.4 车位框局部坐标系草图

```text
局部坐标中的 parking_zone

        z+
        ↑
┌────────────────────┐
│  ○            ○    │
│                    │
│  ○            ○    │
└────────────────────┘
        ↓
        z-

四个轮点都在框内 => success
```

## 8.5 边界判定口径

需要明确“压在线上算不算在框内”。

MVP 建议：

- 轮点落在边界线上，视为在框内

即判定采用：

- `abs(localX) <= width / 2`
- `abs(localZ) <= length / 2`

原因：

- 用户体验更宽容
- 可减少浮点误差带来的边界抖动

## 8.6 是否要求车辆静止

当前 PRD 已明确：

- MVP 不强制要求车辆速度为 0

也就是说：

- 只要四轮都入框，即可成功

后续增强版可考虑追加：

- 速度阈值要求
- 朝向容差要求
- 停稳持续时间要求

## 8.7 风险点

四轮入框判定的关键风险：

- 轮点计算位置不准
- 车位框旋转后坐标转换错误
- 轮点在边界附近抖动导致结果不稳定

MVP 建议：

- 成功一旦触发立即锁定
- 不要求连续多帧保持

## 9. 判定线成功规则设计

## 9.1 规则定义

若车辆车头参考点越过某个 `trigger_line`，则判定成功。

## 9.2 判定对象

### 目标对象

- `goal.type = trigger_line`

### 车辆参考点

- 车头参考点

车头参考点建议定义为：

- 车辆中心沿前进方向偏移到前保险杠附近的一个点

## 9.3 几何思路

判定线本质上是地面上的一条可旋转线段。

成功不只是“当前点在线另一侧”，更重要的是：

- 点发生了穿越

因此建议基于“上一帧位置”和“当前帧位置”进行过线判断。

## 9.4 推荐判定逻辑

对于一条判定线：

1. 计算车头点上一帧相对线的符号
2. 计算车头点当前帧相对线的符号
3. 若符号发生变化，说明车头点穿过了线
4. 再判断穿越点是否在线段有效长度范围内
5. 若是，则成功

## 9.5 判定草图

```text
       车头点移动方向
            ↓
            ● (current)
────────────┼────────────  trigger_line
            ○ (previous)

previous 和 current 分居线两侧
且穿越位置在线段有效范围内
=> success
```

## 9.6 为什么不能只看“当前点在线另一边”

如果只看当前点位置，会出现误判：

- 地图初始化时车头点本来就在“成功侧”
- 重置后直接被判成功
- 短时间跳跃导致穿线过程丢失

因此：

- 必须采用“跨线事件”而不是“落点状态”

## 9.7 线段有效范围

判定线不仅有方向，还有长度。

因此必须同时满足：

- 车头点跨过了无限延长线
- 穿越位置落在线段实际长度投影范围内

否则会出现：

- 在判定线远端延长线上也被错误判成功

## 9.8 单向与双向

MVP 当前推荐：

- 默认双向触发

即：

- 不论从哪一侧穿过，只要过线即成功

后续可扩展：

- `directional = true`
- 仅允许从起始侧向目标侧穿过

## 10. 多成功目标并存设计

## 10.1 目标集合规则

一张地图的 `goals[]` 可同时包含：

- 一个或多个 `parking_zone`
- 一个或多个 `trigger_line`

## 10.2 判定策略

MVP 推荐：

- 顺序遍历所有启用中的目标
- 任一目标成功则直接结束成功检测

伪流程：

```text
for goal in enabledGoals:
  if goal.type == parking_zone and isParkingSuccess(goal):
    success
  if goal.type == trigger_line and isTriggerLineSuccess(goal):
    success
```

## 10.3 为什么不用“全部完成才成功”

因为当前产品定位强调：

- 单次训练快速闭环
- 结果简单明确

若改为“全部完成才成功”，会导致：

- 规则复杂度升高
- 用户理解成本上升
- 地图设计者更难配置

因此 MVP 阶段坚持：

- 任一目标达成即可成功

## 11. 规则优先级设计

## 11.1 失败优先于成功

若同一帧既发生失败条件又发生成功条件：

- 以失败为准

## 11.2 同类多个成功目标的优先级

若同一帧同时满足多个成功目标：

- 对最终结果没有区别，都记为成功

若需要显示“因哪个目标成功”，可采用以下策略之一：

- 返回遍历命中的第一个目标
- 返回最先被设计为高优先级的目标

MVP 建议：

- 返回第一个命中的目标 ID 即可

## 12. 重置规则设计

## 12.1 触发方式

MVP 建议支持：

- 用户手动点击重置
- 用户按下重置快捷键

是否自动重置：

- 建议先不自动重置

原因：

- 用户需要看清为什么失败或成功
- 自动重置会打断学习反馈

## 12.2 重置内容

执行重置时，建议恢复：

- 车辆位置到 `spawnPoint.position`
- 车辆朝向到 `spawnPoint.rotation`
- 车辆速度归零
- 车辆转向角归零
- 训练状态恢复到 `idle`
- 过线相关历史状态清空
- HUD 提示可清空或短暂保留

## 13. 规则调试建议

为了避免实现后“规则对不上感觉”，建议从设计阶段就考虑调试可视化。

## 13.1 推荐调试显示项

- 车辆主碰撞盒
- 四个轮点
- 车头参考点
- 车位框边界
- 判定线方向与长度
- 地图边界
- 当前训练状态
- 当前命中的目标 ID

## 13.2 调试价值

这些可视化对以下问题尤其有帮助：

- 明明进框了却没成功
- 明明没碰到却被判失败
- 判定线看着过了但没有成功

## 14. 边界情况清单

## 14.1 车辆出生点直接处于成功区域

可能情况：

- 出生点被放在车位框内
- 出生点前方就跨过判定线

MVP 建议：

- `idle` 状态不触发成功判定
- 只有进入 `running` 后才允许成功

## 14.2 车辆出生点与障碍物重叠

MVP 建议：

- 编辑阶段尽量阻止这种配置
- 若仍发生，进入 `running` 后立即失败也可以接受

更理想方案：

- 保存地图时提示非法配置

## 14.3 高速跨越判定线漏判

虽然项目是低速训练，但仍可能发生：

- 上一帧在线一侧
- 下一帧已经在线另一侧较远位置

若只看落点容易漏判。

MVP 建议：

- 使用上一帧与当前帧的跨线检测

## 14.4 轮点刚好卡在车位边界

MVP 建议：

- 边界算入内

## 14.5 成功后继续移动

MVP 建议：

- 成功一旦触发立即锁定结果
- 停止本轮进一步失败判定

## 14.6 失败后继续滑动

MVP 建议：

- 失败一旦触发立即锁定结果
- 车辆输入停止
- 车辆速度归零或尽快归零

## 15. 推荐结果数据结构

为了便于 HUD 与日志记录，规则系统可输出统一结果对象。

设计示意：

```ts
type TrainingResult =
  | { status: "idle" }
  | { status: "running" }
  | {
      status: "success";
      reason: "parking_zone" | "trigger_line";
      goalId: string;
    }
  | {
      status: "failure";
      reason: "collision" | "out_of_bounds";
    };
```

这样做的好处：

- HUD 容易展示文案
- 调试信息更清晰
- 后续接入统计与回放也更方便

## 16. MVP 规则验收用例建议

## 16.1 失败规则验收

- 车辆轻微接触围墙，应失败
- 车辆碰到静态轿车，应失败
- 地图开启边界失败时，车辆出界应失败
- 地图关闭边界失败时，车辆出界不应失败

## 16.2 车位成功验收

- 四轮全部入框，应成功
- 只有三轮入框，不应成功
- 轮点压在线上，应成功
- 车辆高速穿入框中，不要求停稳，也应成功

## 16.3 判定线成功验收

- 车头穿过判定线，应成功
- 车身其他部位过线但车头未过线，不应成功
- 车头从延长线区域穿过，但不在线段长度内，不应成功
- 出生时已经在线另一侧，不应立即成功

## 16.4 多目标并存验收

- 同图存在车位框和判定线时，任一目标达成即成功
- 同帧满足多个成功目标，结果仍应为一次成功
- 同帧成功且碰撞，结果应为失败

## 17. 未来增强方向

这份规则文档刻意压制了复杂度。后续可逐步增强：

- 车位方向容差
- 速度必须接近 0
- 停稳持续时间要求
- 判定线单向要求
- 多阶段任务链
- 分数和评级
- 压线但未碰撞的轻微扣分逻辑

## 18. 结论

MVP 阶段最重要的不是做很多规则，而是把少量规则做稳。

当前最合适的规则组合是：

- 失败：碰撞障碍物、可选出界失败
- 成功：四轮入车位框、车头过判定线
- 优先级：失败优先
- 结果锁定：成功或失败后停止本轮判定

这套规则足够简单，也足够支撑停车训练的基本价值。
