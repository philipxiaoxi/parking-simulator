# 停车训练驾驶模拟器 Web 技术架构设计草案

## 1. 文档信息

- 文档名称：Web 技术架构设计草案
- 关联文档：`PRD.md`
- 文档版本：v0.1
- 文档日期：2026-04-17
- 文档目标：用于指导 Web 版 MVP 的技术方案设计与实现规划

## 2. 设计目标

本设计文档聚焦于基于 Web 技术栈实现停车训练驾驶模拟器的首版 MVP。

目标不是构建完整的高拟真驾驶游戏，而是以浏览器为载体，快速实现以下核心闭环：

- 地图创建与编辑
- 3D 上帝视角查看与操作
- 车辆低速驾驶模拟
- 碰撞失败判定
- 停车成功判定
- 判定线成功判定
- 地图本地保存与再次加载

## 3. 架构原则

### 3.1 核心原则

- 表现 3D，规则 2.5D
- UI 与场景渲染分层
- 车辆运动逻辑与物理引擎解耦
- 数据优先，地图结构优先 JSON 化
- 编辑模式与驾驶模式严格分离
- MVP 功能克制，避免过早做复杂编辑器

### 3.2 关键判断

本项目虽然展示为 3D 场景，但本质上是一个平面停车训练系统：

- 所有主要逻辑发生在地面平面
- 车辆只考虑平面位置与朝向
- 障碍物主要采用简化碰撞体
- 成功与失败判定优先基于几何关系而非复杂刚体模拟

这意味着：

- 不建议让完整刚体物理主导车辆驾驶体验
- 更适合“自定义车辆运动 + 物理引擎辅助碰撞检测”

## 4. 推荐技术栈

## 4.1 前端基础

- 框架：React
- 语言：TypeScript
- 构建工具：Vite

理由：

- React 适合承载地图列表、表单、控制面板和交互状态
- TypeScript 适合描述地图结构、规则配置、场景对象等复杂数据
- Vite 适合快速构建与调试 3D Web 项目

## 4.2 3D 场景层

- 渲染引擎：Three.js
- React 集成层：React Three Fiber
- 常用辅助库：@react-three/drei

理由：

- Three.js 生态成熟
- React Three Fiber 能让 React UI 与 3D 场景更自然协同
- drei 可减少相机、控制器、辅助工具的重复工作

## 4.3 碰撞与物理

- 物理库：Rapier
- React 绑定：@react-three/rapier

使用原则：

- Rapier 主要负责障碍物碰撞和基础空间检测
- 车辆移动建议由业务层自主计算
- 不建议 MVP 依赖 Rapier 原生车辆物理来驱动车辆

## 4.4 状态管理

- 状态库：Zustand

适用范围：

- 当前地图
- 编辑模式状态
- 驾驶模式状态
- 选中对象
- 训练结果状态
- UI 面板显示状态

理由：

- 状态轻量
- 学习成本低
- 适合中小型交互型项目

## 4.5 数据持久化

MVP 推荐方案：

- 地图索引：localStorage
- 地图详细数据：IndexedDB

理由：

- localStorage 可快速存少量元数据
- IndexedDB 更适合保存完整地图 JSON
- 后续如需云端同步，可平滑替换为 API 存储

## 4.6 UI 层

- 样式：CSS Modules 或普通 CSS
- 组件策略：优先自建轻量组件

建议：

- MVP 阶段不引入过重的后台 UI 框架
- 重点保证控制面板和编辑面板清晰易用

## 6. 页面与信息架构

## 6.1 页面建议

MVP 建议先采用两页结构：

- 地图列表页
- 地图编辑与训练页

### 地图列表页

功能：

- 查看已有地图
- 新建地图
- 编辑地图
- 开始训练
- 删除地图

### 地图编辑与训练页

该页内部再切分为两个主模式：

- 编辑模式
- 驾驶模式

这样可以降低页面跳转复杂度，同时保证用户在同一场景内完成“编辑后立即试跑”。

## 7. 模块拆分建议

## 7.1 App Shell

职责：

- 路由管理
- 全局布局
- 全局消息提示
- 全局键盘事件接入

## 7.2 Map Management 模块

职责：

- 地图列表读取
- 地图创建
- 地图删除
- 地图复制
- 地图保存
- 地图元信息维护

## 7.3 Editor 模块

职责：

- 摆件面板展示
- 放置对象
- 选中对象
- 移动物件
- 旋转物件
- 删除物件
- 设置出生点
- 放置车位框
- 放置判定线

MVP 建议不做：

- 缩放自由变形
- 复杂多选
- 图层系统
- 复杂撤销栈

## 7.4 Scene 模块

职责：

- 地面渲染
- 障碍物渲染
- 车辆渲染
- 车位框渲染
- 判定线渲染
- 相机控制
- 选中态高亮
- 调试辅助渲染

## 7.5 Simulation 模块

职责：

- 接收输入
- 推进车辆状态
- 执行碰撞判定
- 执行成功判定
- 触发失败或成功状态
- 处理重置

这是业务核心模块，建议与 React 组件尽量解耦。

## 7.6 Rule Engine 模块

职责：

- 解析地图中的成功目标配置
- 处理多种成功目标并存
- 统一输出成功判定结果

本模块建议从 Simulation 中拆出，以便后续扩展：

- 车位成功
- 判定线成功
- 连续经过多个点成功
- 课程任务成功

## 7.7 Persistence 模块

职责：

- 保存地图 JSON
- 读取地图 JSON
- 维护地图索引
- 数据迁移与版本兼容

## 8. 模式切换设计

## 8.1 编辑模式

特点：

- 支持操作场景对象
- 禁止驾驶输入
- 启用物体选中与拖拽
- 显示对象属性面板

## 8.2 驾驶模式

特点：

- 禁止编辑器对象操作
- 启用车辆控制
- 启用成功失败判定
- 启用重置逻辑

## 8.3 状态流草图

```text

   ↓
进入编辑模式
   ↓
保存地图
   ↓
切换驾驶模式

   ↓
开始驾驶
   ↓
┌───────────────┬───────────────┐
│ 碰撞失败        │ 满足成功规则      │
└──────┬────────┴──────┬────────┘
       ▼               ▼
    失败状态          成功状态
       │               │
       └──────→ 重置 / 再次练习
```

## 10. 车辆模型设计

## 10.1 车辆表示方式

车辆建议拆成两层：

- 视觉层：3D 模型或简化低模车
- 规则层：车辆几何参数和参考点

规则层应至少维护：

- 车体中心点
- 朝向角
- 轴距
- 车宽
- 前悬、后悬
- 四个车轮参考点
- 车头参考点

## 10.2 车辆状态建议

```ts
type VehicleState = {
  position: { x: number; z: number };
  heading: number;
  speed: number;
  steeringAngle: number;
};
```

## 10.3 车辆运动建议

MVP 建议采用简化低速 Ackermann 风格运动模型：

- 前进和倒车影响速度方向
- 左右控制改变转向角
- 转向角影响车辆 heading 变化
- 松开按键后速度和转向可逐步回归

建议策略：

- 使用固定时间步长更新
- 车辆运动由业务层计算
- 再把结果同步给渲染层和碰撞检测层

## 11. 碰撞与判定设计

## 11.1 碰撞判定

MVP 可采用以下策略：

- 障碍物使用盒体碰撞器
- 车辆使用一个主车身碰撞盒
- 若车身碰撞盒与任一障碍物相交，则判定失败

补充建议：

- 视觉模型和碰撞盒不必完全一致
- 优先保证碰撞结果稳定可理解

## 11.2 车位成功判定

规则要求：

- 车辆四个车轮都进入车位框内才算成功

建议实现方式：

- 根据车辆参数实时计算四个轮子的世界坐标
- 将四个轮点转换到车位框局部坐标系
- 若四个轮点均落在车位框矩形范围内，则满足停车成功条件

草图：

```text
车位框局部空间

┌────────────────────┐
│  ○            ○    │
│                    │
│  ○            ○    │
└────────────────────┘

四个轮点均在框内 => 成功
```

## 11.3 判定线成功判定

规则要求：

- 车辆车头参考点通过判定线即成功

建议实现方式：

- 定义车头参考点
- 每帧检查其相对判定线的位置
- 当车头参考点从线的一侧移动到另一侧时，判定为通过

草图：

```text
       车辆前进方向
            ↓
         [车头点]
            ●
────────────┼────────────  判定线

车头点越线 => 成功
```

## 11.4 多成功规则并存

同一张地图允许：

- 车位成功规则
- 判定线成功规则

MVP 建议逻辑：

- 只要任意一个成功规则满足，即视为训练成功

后续可扩展：

- 必须依次满足多个目标
- 满足所有目标才成功
- 不同目标对应不同得分

## 12. 相机与交互设计

## 12.1 相机目标

需要同时兼顾：

- 编辑时全局观察
- 驾驶时持续看清车辆和障碍物关系

## 12.2 相机策略

MVP 建议使用轨道相机：

- 支持拖拽旋转
- 支持缩放
- 支持平移目标点
- 默认保持斜俯视角

驾驶模式建议：

- 默认仍为上帝视角
- 不强制跟车第一视角
- 可增加轻微跟随，使用户不易丢失车辆位置

## 13. Zustand 状态设计建议

## 13.1 Store 划分建议

建议拆为以下几类 store：

- `mapStore`
- `editorStore`
- `simulationStore`
- `uiStore`

## 13.2 mapStore

维护：

- 当前地图数据
- 地图列表
- 加载状态
- 保存状态

## 13.3 editorStore

维护：

- 当前模式是否为编辑模式
- 当前选中对象 ID
- 当前工具类型
- 是否启用网格吸附

## 13.4 simulationStore

维护：

- 车辆状态
- 当前驾驶输入状态
- 当前训练状态
- 碰撞状态
- 成功状态
- 重置逻辑

## 13.5 uiStore

维护：

- 面板开关
- Toast/提示
- HUD 内容
- 调试信息开关

## 15. 开发阶段建议

## 15.1 第一阶段：最小技术验证

目标：

- 浏览器中成功渲染 3D 地面和一辆车
- 相机可拖拽缩放
- 键盘控制车辆前进后退转向
- 障碍物可渲染

这个阶段主要验证：

- Web 3D 技术栈是否顺手
- 车辆运动模型是否稳定

## 15.2 第二阶段：训练闭环验证

目标：

- 加入碰撞失败
- 加入重置
- 加入车位成功判定
- 加入判定线成功判定

这个阶段主要验证：

- 训练玩法是否成立
- 判定逻辑是否稳定可理解

## 15.3 第三阶段：编辑器验证

目标：

- 可放置障碍物
- 可设置出生点
- 可放置车位框
- 可放置判定线
- 可保存与再次加载

这个阶段主要验证：

- 用户是否能构建自己的练习地图

## 15.4 第四阶段：可交付 MVP

目标：

- 地图列表
- 地图编辑与训练切换
- 稳定的成功失败反馈
- 较完整的 UI 体验

## 16. 主要风险

## 16.1 编辑器工作量失控

Web 版最容易超预期的不是驾驶，而是编辑器交互本身。

控制建议：

- MVP 只支持单选
- 只支持平面移动和旋转
- 不做复杂自由缩放
- 不做高级层级关系

## 16.2 车辆手感不稳定

如果过早完全依赖物理引擎，车辆可能会出现：

- 抖动
- 滑移
- 倒车表现异常

控制建议：

- 车辆运动逻辑自己掌控
- 物理引擎主要做碰撞辅助

## 16.3 判定逻辑与视觉不一致

如果车位框、判定线、车辆参考点的几何定义不统一，用户会觉得“明明进去了却没成功”。

控制建议：

- 明确所有判定基于同一坐标体系
- 提供调试可视化辅助

## 16.4 本地存储演进成本

MVP 用本地存储没有问题，但未来如果做分享与云端同步，需要考虑数据迁移。

控制建议：

- 从第一版开始给地图结构加 `version`
- 把持久化读写集中在 persistence 模块

## 17. 开工前建议再确认的 5 个点

- 车辆是否仅支持一种默认车型
- 地图边界是否作为强制失败区
- 车位框是否允许旋转放置
- 判定线是否需要单向生效
- 驾驶模式是否支持触屏按钮

## 18. 结论

Web 技术栈完全可以承载本项目的 MVP，但前提是严格坚持“轻模拟、重训练、弱编辑器”的路线。

最优策略不是追求真实车辆物理，而是建立一个：

- 浏览器可访问
- 3D 可观察
- 规则清晰
- 判定可靠
- 可编辑可复用

的低速停车训练系统。

若后续继续深化设计，下一份最值得产出的文档建议是：

- 地图 JSON Schema 详细设计
- 判定规则设计草案
- 交互原型草图
- MVP 开发任务拆解
