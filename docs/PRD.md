# 停车训练驾驶模拟器 PRD

## 1. 文档信息

- 产品名称：停车训练驾驶模拟器
- 文档版本：v0.1
- 文档日期：2026-04-17
- 文档状态：需求梳理与技术预研稿

## 2. 产品背景

现实生活中，很多用户在低速控车场景下存在明显困难，尤其是在倒车入库、侧方位停车、窄路停车、复杂城乡结合道路低速通行等场景中，常因车身空间感不足、方向控制不熟练、缺少安全练习环境而产生焦虑与失误。

为了降低练习门槛，提升用户对车辆空间关系和基础控车技巧的理解，拟开发一款以“上帝视角”进行操作的驾驶模拟软件。用户可在简洁的 3D 场景中控制车辆前进、后退、转向，在地图中完成停车与低速绕障练习，并通过碰撞反馈、重置机制和目标判定逐步建立空间感与操作习惯。

## 3. 产品定位

本产品定位为一款面向停车与低速驾驶训练的轻量模拟器，而非完整驾驶游戏。

核心价值：

- 通过上帝视角降低认知难度，帮助用户理解车头、车尾与轨迹关系
- 提供低风险、低成本、可重复的停车练习环境
- 通过自定义地图与预置场景覆盖常见停车与窄路通行问题

不作为当前阶段目标的方向：

- 高速行驶体验
- 复杂交通系统和 AI 车辆
- 写实级画面表现
- 真实机动车驾考完整流程还原

## 4. 目标用户

### 4.1 核心用户

- 刚拿驾照、实际停车经验不足的新手司机
- 长期不开车、重新上路前希望恢复手感的用户
- 对倒车、侧方位、窄路会车等场景有心理压力的用户

### 4.2 次级用户

- 驾校教练或教学机构，用于演示低速控车原理
- 需要制作教学案例的内容创作者
- 对车辆空间感训练感兴趣的普通用户

## 5. 用户痛点

- 对车身长度、宽度、转弯半径缺乏直观理解
- 倒车时难以判断车尾轨迹与障碍物距离
- 现实练车成本高，出错压力大
- 同一停车场景难以稳定重复练习
- 许多教学技巧停留在口头层面，缺少可操作演示环境

## 6. 产品目标

### 6.1 业务目标

- 验证“上帝视角停车训练”是否能帮助用户理解基础控车技巧
- 构建可快速扩展的停车练习产品原型
- 形成地图编辑能力，为后续课程化训练、场景分享打基础

### 6.2 用户目标

- 理解车辆前进、后退、转向后的轨迹变化
- 在反复练习中提升停车成功率和空间判断能力
- 能在自定义或预置地图中练习常见低速场景

### 6.3 成功指标建议

- 新用户可在 5 分钟内理解基础操作
- 用户可独立完成一次地图加载、驾驶、碰撞失败、重置再练习的完整闭环
- 在预置场景中具备明确成功/失败结果

## 7. 核心使用场景

### 场景一：倒车入库练习

用户进入预置练习场景，观察车位与障碍物位置，控制车辆前进、倒车与转向，尝试将车停入目标车位。若碰撞则立即失败并重置到起点。

### 场景二：侧方位停车练习

用户在道路边停车区域进行多次尝试，通过上帝视角观察车身与前后车辆、围墙、车位线之间的关系，学习不同转向时机。

### 场景三：窄路低速通行

用户在复杂狭窄道路中以低速移动，训练车身宽度判断能力和转向空间感。

### 场景四：自定义教学地图

用户或教练通过地图编辑器摆放房子、围墙、车辆模型和车位框，构造适用于教学的特殊道路或停车环境。

## 9. 功能需求

## 9.1 地图管理

### 功能描述

用户可创建、查看、编辑、删除地图，并从地图列表中选择地图进入编辑或训练。

### 需求列表

- 支持新建地图
- 支持地图重命名
- 支持查看地图列表
- 支持编辑已有地图
- 支持删除地图
- 地图应保存基础信息，如名称、尺寸、创建时间、更新时间

### 建议补充

- 地图支持封面缩略图
- 地图列表支持按时间排序
- 地图支持复制

## 9.2 地图编辑器

### 功能描述

用户可在 3D 上帝视角中编辑训练场景，摆放障碍物和车位，设置车辆初始位置。

### 摆件清单

- 轿车模型，仅作为静态障碍物
- SUV 模型，仅作为静态障碍物
- 矩形
- 正方形
- 房子
- 围墙
- 车位框
- 判定线

### 需求列表

- 支持从摆件面板选择物件
- 支持在地图中放置物件
- 支持移动已放置物件
- 支持旋转物件
- 支持删除物件
- 支持设置车辆初始位置与初始朝向
- 支持放置判定线并调整位置、朝向
- 支持相机拖动、缩放、旋转观察场景

### 体验建议

- 建议支持网格吸附，提高摆放效率
- 建议支持简单撤销/重做
- 建议使用低多边形简洁风格，减少美术成本

## 9.3 驾驶操作

### 功能描述

用户在训练地图中驾驶一辆可控车辆，通过前进、后退和转向完成停车或绕障练习。

### 需求列表

- 支持左转
- 支持右转
- 支持前进
- 支持后退
- 支持车辆重置到初始位置
- 支持开始训练与结束训练的基本状态切换

### 输入方式建议

- 优先支持键盘操作
- 可同时提供界面按钮供触屏或鼠标点击

### 操控原则建议

- 车辆运动应尽量贴近低速停车场景
- 不追求复杂真实物理，但应保证转向与车身轨迹规律可信

## 9.4 规则判定

### 失败条件

- 车辆与任一障碍物发生碰撞
- 车辆越出地图边界（如定义边界）

### 失败反馈

- 弹出或展示失败提示
- 允许用户手动重置
- 可根据模式选择自动重置到初始位置

### 成功条件

MVP 版本中加入以下成功判定：

- 若地图中配置了目标车位框，车辆四个车轮均进入车位框内，则判定成功
- 若地图中配置了判定线，车辆在未碰撞前提下车头通过判定线，则判定成功
- 同一张地图允许同时存在“车位成功”和“出线成功”两种目标，满足任一成功条件即可判定成功

### 成功判定建议细则

- 停车成功以四轮全部进入车位框范围内作为 MVP 判定标准
- 判定线成功以车头参考点越过判定线作为 MVP 判定标准
- 可在后续版本中增加朝向容差、压线检测、速度为零等更严格条件
- 判定线更适合“驶出场景”“窄路通过场景”“出库场景”等非停车类训练目标
- 单张地图支持多种成功目标并存，便于覆盖复合练习场景

## 9.5 训练反馈

### MVP

- 显示当前练习状态
- 显示碰撞失败提示
- 显示成功提示
- 提供重置按钮

### 后续增强

- 显示停车是否成功
- 显示失败原因
- 统计尝试次数
- 显示练习耗时
- 提供简单操作建议

## 10. 非功能需求

### 10.1 视觉表现

- 场景采用简单、清晰、低多边形风格
- 优先保证物体边界清晰、空间关系易识别
- 不以写实美术为目标

### 10.2 性能

- 在常见消费级设备上流畅运行
- 以中小型地图为主要目标
- 单地图应能容纳足够数量的训练摆件而不明显卡顿

### 10.3 易用性

- 新用户应快速理解基本操作
- 地图编辑器交互应直观，尽量减少复杂参数设置
- 失败和重置流程应简洁明确

### 10.4 可扩展性

- 地图数据与摆件定义应可扩展
- 后续可接入更多车型、练习模式与评分逻辑

## 12. 技术方案预研

## 12.1 技术目标

技术方案应优先服务以下目标：

- 快速搭建停车训练核心玩法
- 低成本实现 3D 场景与上帝视角
- 便于实现地图编辑器
- 降低复杂物理带来的研发风险

## 12.2 推荐技术方向

推荐采用：

- 低模 3D 场景表现
- 平面化车辆运动模型
- 简化碰撞与判定系统

即“视觉 3D + 运动 2.5D”的方案：

- 用户看到的是 3D 场景
- 车辆实际只在地面平面移动
- 核心只计算位置、朝向、碰撞关系
- 不引入完整真实汽车物理

该方案更适合本项目“停车训练”而非“驾驶竞速”的定位。

## 12.3 引擎/框架选型比较

### 方案 A：Godot 4

优点：

- 适合中小型 3D 模拟项目
- 自带场景系统、碰撞、相机与 UI 能力
- 原型开发速度快
- 适合从 0 到 1 验证玩法
- 低模风格适配度高

缺点：

- 若未来重点转向 Web 在线产品，生态整合不如 Web 技术自然
- Web 导出可行，但需提前验证性能与兼容性

适用判断：

- 适合优先做桌面原型
- 适合先验证玩法与训练价值

### 方案 B：Web 技术栈

推荐组合：

- React 或 Vue
- Three.js 或 React Three Fiber
- Rapier 或 Cannon 负责碰撞

优点：

- 用户通过浏览器即可访问
- 列表、表单、编辑器控制面板开发方便
- 后续接入账号、分享、社区内容更自然

缺点：

- 3D 编辑器交互开发成本更高
- 相机、拖拽、碰撞、摆件操作等需要更多自定义工程
- 原型期调试成本偏高

适用判断：

- 适合明确以 Web 产品形态为主
- 适合前端能力较强的团队

### 方案 C：Unity

优点：

- 3D 工具链成熟
- 商业产品可扩展性强
- 资料丰富

缺点：

- 对当前需求而言偏重
- 初期工程复杂度较高

适用判断：

- 适合已有 Unity 经验团队
- 适合明确面向移动端或商业化深入开发

## 12.4 当前推荐

若当前目标是快速验证产品方向，推荐优先使用 Godot 4 实现首版原型。

推荐理由：

- 可较低成本完成 3D 场景与相机控制
- 地图编辑器实现成本相对更低
- 更适合先验证“停车训练是否有效”这一核心问题

## 13. 风险与难点

### 13.1 过度追求真实物理

如果初期引入完整车辆刚体物理，将显著增加开发成本与调参难度，并不利于 MVP 落地。当前更适合以可信的简化低速运动模型为主。

### 13.2 地图编辑器复杂度高于预期

编辑器往往是项目中最容易被低估的模块，尤其是以下能力：

- 选中
- 拖拽
- 旋转
- 删除
- 相机控制
- 保存与加载

建议在 MVP 中严格限制编辑能力范围。

### 13.3 训练闭环不完整

若只有“碰撞失败”而没有“成功判定”，产品更像沙盒而非训练器。建议在第二阶段尽快补入目标车位和成功规则。
若成功判定过于宽松，用户可能“形式上成功”但没有真正学会规范停车；若成功判定过严，又会影响早期可玩性。MVP 建议采用易理解、易达成的基础成功规则，后续再逐步提高标准。

### 13.4 教学价值依赖反馈系统

用户是否真正学到技巧，不仅取决于能否驾驶，还取决于是否提供足够清晰的结果反馈与可重复练习机制。

## 16. 结论

本项目具备明确的用户痛点和清晰的 MVP 方向，适合从“停车训练”这一垂直场景切入。当前最合理的路线是以简洁低模 3D 场景承载上帝视角交互，以平面化车辆运动和清晰规则判定构建训练闭环，并通过地图编辑器提高场景适配性与扩展能力。

建议下一步优先产出以下文档之一：

- MVP 功能拆解与优先级清单
- 技术架构设计文档
- 交互原型草图
- 开发迭代计划
